# 交付与验收记录

## 当前目标和审计结论

原仓库为空。本轮在已有基础工作台上继续开发，按用户“尚无站点”的实际情况，增加内置商店作为第一条站点主线，保留WordPress/WooCommerce作为可选连接。原始方案仍是目标设计，不能把本文的受控测试当成真实市场、供应、支付或获客证据。

## 数据与界面

新增独立账号与会话、项目归属、结构化档案及版本、阶段状态、计划、任务协议、审批、资料文件、外部连接及操作台账、外部导入、期间费用、商店与结账、支付事件和成本核对状态。旧表不删除，旧项目归管理员。所有新增实体按项目隔离，结构化档案更新有版本冲突检查与历史记录。

原有七个页面增加结构化商品/供应/报价/样品/风险、阶段闸口、审批、自动派工、文件、工单、经营结果、账号及连接器入口。公开商店页面显示商品、售价、库存、配送、退换政策、购物车和结账模式。当前没有商品真实图像/视频制作流水线。

## T01–T18 验收边界

- T01–T06：表单启动、缺口、来源/成本闸口、样品等待与版本返工已具备程序路径。实际业务资料仍需用户提供。
- T07：WordPress及Stripe超时不自动重发的规则已用受控返回验证；没有进行真实平台超时演练。
- T08–T15：重复订单、重复支付事件、并发预算、授权撤销、队列中断、成本未知、资料更正、退款与人工接管有测试覆盖。没有声称外部支出已被中台实际拦截，当前仅实现已接入工具的前置控制与本地预算限制。
- T16：真实HTTP请求验证跨账号读取、修改、导出、文件下载和管理账号均被拦截；模型上下文按项目读取，工单不会默认发送给生成任务。
- T17：可记录无效或停止结论并保留历史；没有外部页面变更的通用自动回滚功能。
- T18：受控反馈能创建并执行下一轮任务；真实经营反馈与实际外部执行尚未联调，不能标为完整真实闭环通过。

## 验证方法

SQLite与PostgreSQL共用规则/HTTP测试，PostgreSQL使用专用Docker测试数据库与逐例隔离schema；生产连接地址不用于单元测试。迁移测试验证源库备份、任务/审批复制、日志序列和拒绝覆盖非空目标。

浏览器测试验证密码登录、结构化方向与商品、阶段、审批、文件、独立账号隔离、移动宽度，以及内置商店发布、公开购物车和本地测试下单。所有样例明确标记TEST。

容器网络在本云机器无法解析包索引/代理域名，默认联网安装镜像构建受此限制。另使用PyPI通过TLS与原始发行哈希校验下载的wheel离线构建同一应用进行运行验证；没有禁用TLS或包校验。Render联网构建与实际部署需以其日志为准。

## 外部前提

- 尚无独立站：已改为内置商店，不要求用户先购买第三方站点。
- AI模型、外部研究工具、真实图片/视频生成仍需服务选择、授权和实际联调。
- 真实Stripe商户身份、密钥和Webhook签名必须由经营者在部署平台配置；本地测试不能代替这些前提。
- 可选WordPress/WooCommerce需要用户已有站点及官方应用密码。
- 免费实例不能保证本地数据保留，长期使用需配置实际PostgreSQL或持久磁盘并演练恢复；没有替用户购买数据库。

## 恢复与回滚

新增表采用IF NOT EXISTS；保留旧项目、任务和记录。回滚前停止服务，备份数据库和源码。切换PostgreSQL前使用迁移工具检查；源库与备份不删除。外部发送中的操作重启后标为结果未知，不自动补发。商店可以下线以阻止新结账，已发生支付仍接收验签核对。代码回滚前需确认新数据表不会被旧界面误解释。
